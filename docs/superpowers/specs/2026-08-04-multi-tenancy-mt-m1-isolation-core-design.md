# Multi-Tenancy MT-M1 — Isolation Core: Design

**Scope of this document:** MT-M1 only — second of four milestones in the PRD (MT-M0 Foundations → **MT-M1 Isolation core** → MT-M2 Multi-facility + front door → Exit). MT-M0 shipped the schema, RLS policies, `withTenantScope` helper, and the CI scoping guard as foundations, without wiring any route handler to real tenant context. MT-M1 is where that wiring actually happens and gets proven.

**PRD requirements covered:** TEN-001 (remaining part), TEN-002, TEN-005, TEN-007. TEN-003 and TEN-006 are already satisfied by MT-M0/prior work (see below). TEN-008/010/012/013/014 are explicitly MT-M2/Exit.

## 1. Current-state audit (done before any design decision below)

- **TEN-003 (fixed one-room-per-stage, per facility): already satisfied.** `roomsTable` is per-facility rows with a closed `roomNameEnum` (seeding/fertigation/harvesting) and `UNIQUE(facility_id, name)`; `POST /facilities` creates exactly 3 rooms atomically in the same transaction as the org+facility. No UI (admin-dashboard or farmeasy) exposes room count or names — confirmed via repo-wide grep, zero hits. Farmeasy (mobile) has zero room/stage-related code at all today, so there is no "mobile validation copy matrix" to shrink — nothing to remove. The only real gap is test coverage for TEN-003's specific ACs (two facilities each independently holding a "seeding" row; no UI exposure) — folded into the TEN-007 isolation suite (Task 5) rather than a standalone task.
- **TEN-006 (pilot backfill): done in MT-M0.** Migration series written, rehearsed against a disposable Supabase stack, `docs/runbooks/mt-m0-rehearsal-report.md` records the result.
- **TEN-001 remaining work:** organizations/organization_members/roles already exist (MT-M0 Task 1). What's missing is session-level resolution — today, every route handler does its own ad-hoc `SELECT ... FROM users WHERE id = getAuth(req).userId` to check `organizationId`; there is no shared middleware, and no facility resolution at all.
- **TEN-002 remaining work:** 11 files fail typecheck against the NOT-NULL scoping columns (`alerts.ts`, `badTrays.ts`, `cycles.ts`, `facilityLogs.ts`, `growthProfiles.ts`, `sensors.ts`, `shipments.ts`, `tasks.ts`, `quickbooks.ts`, `overdue-scanner.ts`, plus 3 test files) — tracked in the MT-M0 rehearsal report. Additionally, `inventory.ts`/`seedLots.ts`/`facilities.ts` currently resolve a "pilot-default facility" via `SELECT id FROM facilities ORDER BY id LIMIT 1` — a placeholder that needs retiring now that real context exists. **Separately, and not previously flagged:** `artifacts/api-server/src/lib/metrics/templates.ts` and `custom.ts` (the entire `/api/metrics` dashboard query-template system, 184 lines) have **zero** facility scoping anywhere — confirmed via grep, zero matches for `facility_id`/`facilityId`/`organization_id`. This is invisible to both TypeScript's NOT-NULL column checking (raw `sql.raw` strings, not typed Drizzle inserts) and to `check-tenant-scope.mjs` (which only understands Drizzle chain calls, not raw SQL templates) — meaning the main dashboard endpoint has been silently mixing every organization's data together since it was built, and no existing mechanism would ever have caught it. This is a bigger, separate gap from the 11-file list and gets its own task.
- **TEN-005 remaining work:** `facilities` table already has `timezone`/`units`/`currency` columns (from the onboarding wizard's W2 step). The global `FACILITY_TIMEZONE` env var is still live and baked into `tz.ts`'s `facilityNow()`/`rangeWindow()` helpers, consumed by the same metrics template system above — folded into that task rather than separate, since both need the same "thread a real facility's timezone through the query builder" change.
- **`overdue-scanner.ts` is structurally different from every other flagged file:** it's a scheduled background job (startup + interval, invoked directly in `index.ts`), not an HTTP route handler — there is no request/session to resolve tenant context from. It needs its own pattern: iterate every organization/facility and call `withTenantScope` once per tenant, rather than deriving context from middleware.
- **Environments:** ADR-004 (Accepted) gives a real, separate staging Supabase project (synthetic fixtures only, resettable, no production data copy) with its own Render services. MT-M1's PRD exit criterion — "two test orgs fully isolated in staging" — targets this real environment, not just a disposable local stack. `CLAUDE.md` had a stale line claiming single-environment/no-staging (inherited from ADR-003's original statement, superseded the next day by ADR-004); corrected separately (commit `865d782`).
- **RLS load-bearing prerequisites, carried forward from MT-M0's final review, now blocking rather than just noted:** (a) Task 7's BYPASSRLS check (`scripts/ci/verify-db-role.mjs`) was never run against a real DB — if `DATABASE_URL` uses Supabase's default `postgres`/`service_role` (both `BYPASSRLS`), every RLS policy is a silent no-op; (b) `organization_members`'s own RLS policy scopes on `app.org_id`, but resolving a user's org membership — the very thing the new session middleware needs to do first — is the query that would be blocked before `app.org_id` is ever known. Both need fixing before the middleware can be trusted under enforced RLS, not just documented.

## 2. Architecture

Four pieces, in dependency order:

1. **Session middleware** (new, `artifacts/api-server/src/middlewares/tenantContext.ts`) — after `supabaseAuthMiddleware` verifies the JWT, this resolves `{ organizationId, facilityId, role }` from `organization_members` (join to `facilities` for the org's one facility) keyed on `getAuth(req).userId`, attaches it to `req.tenant`, and rejects with 401 (no resolvable identity) or 403 (identity resolves, but no membership) before any route logic runs. Facility resolution is simply "the org's one facility" — MT-M2's TEN-008 changes this lookup, not the middleware's shape, when multi-facility ships.
2. **Route handler sweep** — rewrite the 11 flagged handlers plus `inventory.ts`/`seedLots.ts`/`facilities.ts` (retiring the pilot-default pattern everywhere, not just where it currently fails) to call `withTenantScope(req.tenant, (tx) => ...)` instead of touching `db` directly. Every handler that accepts a resource ID in the URL (e.g. `GET /shipments/:id`) gets an explicit existence-plus-ownership check that returns 404 for a real ID belonging to another org/facility — a WHERE-clause scope filter alone would already return "not found" for a wrong-tenant row, but this needs a positive test proving it, not an assumption.
3. **Metrics/timezone scoping** (separate task, not folded into the route sweep) — thread `facilityId` (and the real per-facility `timezone`, retiring `FACILITY_TIMEZONE`) through every template in `templates.ts`/`custom.ts` and through `tz.ts`'s helpers. This class of gap is structurally invisible to `check-tenant-scope.mjs` (raw SQL, not Drizzle calls) — noted as a residual risk for a future guard, not blocking this task.
4. **Overdue scanner** — loop over every organization's facility, calling `withTenantScope` once per tenant instead of the current single unscoped query across all cycles.

Supporting infrastructure:

5. **RLS prerequisites** — provision a real least-privilege (non-`BYPASSRLS`) Postgres role on staging first (verified via `verify-db-role.mjs`), rotate `DATABASE_URL` to use it, then production once staging is verified; add an `auth.uid()`-keyed RLS policy on `organization_members` scoped to `user_id = auth.uid()` so the middleware's own membership lookup succeeds under enforced RLS (resolving the chicken-and-egg) without needing `BYPASSRLS`/`SECURITY DEFINER`.
6. **CI guard hardening** — make `check-tenant-scope.mjs` multi-line-aware (parse the Drizzle chain across lines, not a single-line regex), since MT-M1 is precisely when the files it's supposed to gate are being rewritten, and it currently misses `seedLots.ts`'s own multi-line lookup handler.
7. **TEN-007 cross-tenant isolation suite** — integration tests per scoped endpoint: provision org A + org B (each via `POST /facilities`, one facility each), seed a resource under A, assert B's session gets a 404 on direct access and zero rows on list endpoints. Covers all rewired handlers, the metrics endpoint, and TEN-003's rooms cross-facility case. Runs in two contexts: (a) CI, against the disposable Supabase stack (same mechanism as MT-M0's rehearsal), blocking merge; (b) once against real staging with 2 provisioned test orgs, satisfying the PRD's literal MT-M1 exit criterion ("two test orgs fully isolated in staging"). The separate "named production verification job" gating TEN-011/012's sign-up flag remains Exit-milestone scope, not built here.

## 5. Risks and gaps

- **Missed-scope-filter risk (highest severity, per the PRD's own risk register).** A single forgotten `withTenantScope` call anywhere in the 11+ file sweep is a cross-tenant leak. Mitigated in layers — the helper itself, RLS as independent defense-in-depth once the role/policy prerequisites land, the hardened CI guard, and the isolation suite — but no single layer is sufficient alone; a bug in one is only caught because the others are independent, not because any one is exhaustive.
- **The raw-SQL blind spot is structural, not just the one known instance.** `check-tenant-scope.mjs` (even multi-line-aware) can only ever understand Drizzle chain calls. Any `sql.raw(...)` usage anywhere in the codebase — today's metrics templates, or any future one — is invisible to it by construction. MT-M1 fixes the *known* instance (metrics); it does not close the class of gap. Worth a follow-up idea (e.g. a lint rule banning bare `sql.raw` outside an explicit allowlist) but out of scope here — noted so it isn't mistaken for solved.
- **Single-facility-per-org assumption is now baked into route handler code, not just the middleware.** Every handler rewritten in this milestone will read `req.tenant.facilityId` as if it's the only possible facility. When MT-M2 ships TEN-008 (multi-facility), it's not enough to change the middleware's facility lookup — every one of these handlers needs re-auditing to confirm none of them cache, hardcode, or otherwise assume single-facility behavior beyond just reading the field. Flagging now so MT-M2's design doesn't rediscover this from scratch.
- **DATABASE_URL role rotation is a real, mostly-untestable-until-done infra change.** The new least-privilege role might be missing a grant the app actually needs (an INSERT/UPDATE/DELETE privilege on some table no one thought to check) — this would only surface as a production-shaped failure after rotation, not before. Mitigation: staging first, verified functionally (not just via `verify-db-role.mjs`'s BYPASSRLS check — the app's own test suite should run against the rotated staging role before production follows), and keep the prior connection string available for a fast revert.
- **The new `organization_members` `auth.uid()`-keyed policy is itself new attack surface.** It must be scoped tightly to `user_id = auth.uid()` (a user reading only their own membership row) — if it's accidentally written broader (e.g. org-scoped instead of user-scoped), it could leak other members' role/status within the same org, or worse, across orgs if the condition is malformed. Needs the same empirical-review discipline MT-M0 used for `withTenantScope`'s `set_config` bug (test against a real Postgres instance, not just static reading).
- **Staging isolation-suite run creates real rows in a real Supabase project.** Even though staging is documented as resettable with no retention guarantee, the suite should clean up its own 2 test orgs after running (or use an obviously-named/flagged fixture) rather than relying on someone remembering to reset staging later — otherwise repeated runs (e.g. rerunning after a fix) accumulate orphaned test orgs.
- **Overdue scanner's per-tenant loop changes its performance shape.** Today it's one query across all cycles; looping per-organization/facility means N queries at pilot scale (acceptable — one tenant, matching MT-M0's rehearsal) but this doesn't scale past a handful of tenants without batching. Not a concern for MT-M1's actual tenant count, but worth a comment in the code so it isn't mistaken for the final design once tenant count grows.
- **404-vs-empty-result consistency across 11+ independently-rewritten handlers risks drifting.** Without a single shared "assert ownership or 404" helper, each handler's implementer could write a slightly different check, and one could regress to leaking existence (e.g. a 403 instead of 404, revealing the resource exists) without anyone noticing until the isolation suite's assertions are precise enough to catch it. Suggests factoring the ownership-check into `withTenantScope` or a sibling helper rather than leaving it to 11 independent implementations — a decision for the implementation plan, not finalized here.
- **MT-M0's backfill single-facility-assumption finding is not revisited here.** Migrations 0019/0024 already ran (against the disposable rehearsal stack, not production); MT-M1 doesn't re-run or guard them. This remains an open operational precondition for whenever these migrations are eventually replayed against a real environment with more than one facility already present — unlikely to occur but not actively guarded against.
