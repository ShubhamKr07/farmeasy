# ADR-002: Retain Neon Postgres, relocate region, pooled-vs-direct policy

**Status:** Superseded by ADR-003 — the GCP migration this ADR was written for was abandoned before Neon relocation ran; Neon itself is being replaced by Supabase, not relocated. Left in place for historical context on the pooled-vs-direct reasoning, which ADR-003 carries forward.
**Date:** 2026-07-20
**Related:** GCP_IMPLEMENTATION_PLAN.md WS2 (INF-201–INF-205), ADR-004 (domain-mapping / lb_fallback)

## Context

The GCP migration (Render -> Cloud Run us-west2) needs a data-layer decision
independent of the compute decision: keep Neon, or migrate to a GCP-native
Postgres (Cloud SQL, AlloyDB)?

Current production database is Neon, region `aws-us-east-1` (N. Virginia) —
confirmed from the live `DATABASE_URL` host
`ep-round-pond-atuhxbhc.c-9.us-east-1.aws.neon.tech`. This is already far
from both the old compute region (Render, Oregon) and the new one
(GCP us-west2, Los Angeles) — the WS2 relocation is necessary regardless of
which cloud runs compute, not a new cost introduced by this migration.

Neon has no California region. Nearest to us-west2 is `aws-us-west-2`
(Oregon), ~15–20 ms RTT. This was confirmed via Neon's docs
(neon.com/docs/introduction/regions) during the California retargeting of
this plan — see the plan's prerequisites section for the live region list to
re-check before INF-202 actually runs, since Neon has added regions before
(ap-southeast-2 shipped after this plan's source assessment was written) and
could plausibly add a US-West region later.

## Decision

**Retain Neon**, relocate to `aws-us-west-2` (Oregon). Do not migrate to
Cloud SQL or AlloyDB as part of this infra migration.

Reasoning:
- The app's entire data-access layer (Drizzle ORM, migration journal 0000–0005,
  `@workspace/db` package) is Postgres-standard with no Neon-specific
  extensions in use beyond connection pooling — a same-vendor region move is
  a `pg_dump`/`pg_restore` + connection-string swap; a cross-vendor move is a
  schema/tooling migration with meaningfully higher risk for a project this
  plan explicitly scopes as infra-only ("the infra cutover and the tenancy
  schema migration never share a week" — plan timing rule).
- Neon's serverless scale-to-zero and branching model match Cloud Run's own
  scale-to-zero economics — a provisioned Cloud SQL instance would reintroduce
  an always-on cost floor that scale-to-zero Cloud Run was specifically
  chosen to avoid.
- This migration's stated goal (Assessment v1 / Technical Implementation
  Plan v1) is compute relocation, not a database re-platform. Re-platforming
  the database is a separate, larger decision this ADR deliberately does not
  make.

## Watch item: Databricks acquisition of Neon

Databricks announced its acquisition of Neon (2025). As of this writing,
Neon continues to operate its existing product, pricing, and region
footprint under Databricks ownership with no announced deprecation timeline
for the standalone Postgres service. This ADR's decision does not depend on
the acquisition's outcome, but it is a real dependency risk worth tracking:

- **Re-review trigger:** any Databricks announcement of Neon standalone-product
  deprecation, pricing-model change, or region-footprint reduction.
- **Fallback if triggered:** Cloud SQL for Postgres in us-west2 is the
  most direct same-vendor-as-compute fallback (native VPC peering with Cloud
  Run, no egress cost from GCP's own network) and should be the first option
  evaluated, not re-litigated from scratch, if this trigger fires.
- Revisit this section at the WS6 + 30-day cost review (INF-604) regardless
  of whether the trigger has fired, as routine hygiene.

## Pooled vs. direct connection policy

Neon offers two connection endpoints per branch: a PgBouncer-fronted pooled
endpoint and a direct endpoint. Policy, matching current `render.yaml`
practice (`NEON_DATABASE_URL` / `DATABASE_URL` both set to the same pooled
string today) and the plan's INF-203:

| Use | Endpoint | Why |
|---|---|---|
| `farmsmart-api` runtime (`DATABASE_URL` secret) | **pooled** | Cloud Run's per-request/per-instance connection churn under scale-to-zero + concurrency=80 needs PgBouncer's connection multiplexing — a direct connection per concurrent request would exhaust Postgres's own `max_connections` under any real burst (this is exactly what INF-203's k6 VU=50 smoke test is designed to catch). |
| `farmsmart-recommender` runtime (`DATABASE_URL` secret) | **pooled** | Same reasoning — it's also a Cloud Run service with the same connection-churn profile, just lower expected concurrency. |
| `lib/db/scripts/migrate.mjs` (schema migrations) | **direct** | Migrations run DDL and expect session-level guarantees (e.g. advisory locks, `search_path` state) that PgBouncer's transaction-pooling mode does not reliably preserve across statements. Direct-only for this one workload, always. |
| PITR drills / `pg_dump`/`pg_restore` (INF-202, INF-205) | **direct** | Bulk data movement wants a stable, uncontended session; pooled adds overhead and pooling-related edge cases with no upside for a one-shot batch operation. |

Both endpoints are provisioned automatically per Neon branch — this is a
connection-string selection policy, not an infrastructure decision requiring
separate Terraform resources. `infra/envs/{staging,prod}/main.tf` reflects
it: `neon-database-url-pooled` is the only Neon secret wired into either
`run-service` module's `secret_env_vars`; `neon-database-url-direct` exists
as a secret name for migration/drill use but is deliberately not bound to
either Cloud Run service's environment.

## Consequences

- INF-202 (Neon relocation) becomes a same-vendor region move: create new
  Oregon-region project, `pg_dump`/`pg_restore`, re-run
  `lib/db/scripts/migrate.mjs` against the new **direct** URL (expected
  no-op if the journal restored with the data), verify row counts + checksum
  match on `cycles`/`growth_profiles`/`inventory_items`/`seed_lots` per the
  plan's stated Verify.
- No application code changes required — `@workspace/db` already reads
  `DATABASE_URL` from environment/Secret Manager with no region assumption
  baked in.
- Old-region (`us-east-1`) Neon project stays untouched as the data rollback
  until cutover + 7 days (INF-603), per plan rule and GATE G2's exit
  condition.
