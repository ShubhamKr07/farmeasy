# ADR-004: Separate staging and production environments with SHA-gated promotion

**Status:** Accepted
**Date:** 2026-07-27
**Related:** ADR-003 (supersedes its single-environment statement — staging is
now a separate project; Supabase provider and connection-string policy remain
accepted), `docs/runbooks/staging-bootstrap.md` (operational bootstrap
procedure implementing the environments, secrets, and promotion gate defined
here)

## Context

ADR-003 landed Supabase as the Postgres provider on a single project, matching
the then-current Render setup which was itself single-environment. That was
the right call for a verified cutover under time pressure, but it left no
non-production surface to validate against: every deploy went straight to the
only environment that existed, and every schema migration ran against live
production data with no prior staging run.

This ADR introduces the staging/prod split that ADR-003 deliberately deferred.
It is scoped to **environment topology, isolation, retention, and promotion
rules** only — it does not re-litigate the database provider (Supabase,
decided in ADR-003) or the pooled-vs-direct connection policy (decided in
ADR-003's table, which this ADR inherits unchanged).

## Decision

### One separate Supabase staging project; no production data copy

Staging is a **distinct Supabase project** from production. Production data is
never copied, cloned, or branched into staging. Staging is seeded with
synthetic/test fixtures only — it exists to validate code and migrations, not
to mirror live data.

Reasoning:
- Production contains real user data (growth profiles, cycles, inventory).
  Cloning it into staging would needlessly duplicate PII across an environment
  with weaker access controls, expanding the blast radius of any staging
  compromise for no validation benefit.
- Migrations and schema changes need *some* representative schema to run
  against, not the production row set — a freshly-migrated staging schema with
  fixtures exercises the DDL path just as well as a full data copy.

### Staging Render services

Three staging services on Render, mirroring the production topology:

| Staging service | Production counterpart |
|---|---|
| `farmsmart-api-staging` | `farmsmart-api` |
| `farmsmart-dashboard-staging` | `farmsmart-dashboard` |
| `farmsmart-recommender-staging` | `farmsmart-recommender` |

### Staging keeps the current public topology until Release 3

Staging **preserves the current public-recommender / web-dashboard topology**
as it exists in production today. It does *not* adopt the blue-green /
domain-mapped topology in advance. Release 3 performs the blue-green
conversion; until then both staging and production run the same public
topology, so staging validates what production actually runs.

### Database runtime uses transaction pooler; migrations use session pooler

This carries ADR-003's connection-string policy forward verbatim into both
environments — it is restated here only so the staging bootstrap runbook has a
single authoritative reference:

| Use | Endpoint | Port |
|---|---|---|
| App runtime (`DATABASE_URL`) | Transaction pooler | 6543 |
| Migrations (`DATABASE_URL_DIRECT`) | Session pooler | 5432 (`pooler.supabase.co`) |

Both environments follow the same rule. See ADR-003's full table for the
per-workload rationale.

### Production receives only the exact SHA that passed CI and staging

Promotion is **SHA-gated**: the SHA that passed CI must be the same SHA that
deployed to staging and passed staging checks, and only that exact SHA may be
promoted to production. No rebuilds, no "latest on `main`", no branch tips —
a literal commit SHA, pinned through CI → staging → production.

### Staging data may be reset; production migrations remain forward-only

Staging has **no data-retention guarantee** — it may be reset, wiped, or
re-seeded at any time to validate a migration or clear bad state. Production
takes the opposite stance: production migrations are **forward-only**, with
no destructive rollback path. (The old Neon project was retained as rollback
during ADR-003's cutover window per its Task 10; that was a one-time
concession, not a standing policy.)

Reasoning:
- If staging can't be reset, it accumulates state that masks migration bugs —
  the whole point of a separate staging project is that it's disposable.
- Forward-only production migrations force the discipline of testing
  migrations on staging first (which is now possible), rather than relying on
  a rollback that may not be safe for destructive DDL.

## Consequences

- ADR-003's "Single project, no staging/prod split" statement is **superseded**
  by this ADR. ADR-003's Supabase-provider choice and connection-string policy
  remain Accepted and in force.
- Six Render services now exist (three staging + three production) instead of
  three. Cost increases; this is the cost of a real staging surface.
- `render.yaml`, CI workflows, and the promotion workflow must reference the
  exact-SHA gate — "deploy latest" is no longer an acceptable path to
  production. The bootstrap runbook (`docs/runbooks/staging-bootstrap.md`)
  documents the GitHub protected environments, secrets, and variables this
  requires.
- `PRODUCTION_DATABASE_URL_DIRECT` and `PRODUCTION_DATABASE_CA_CERT` (and their
  staging counterparts) are the only production-environment secrets the
  promotion workflow needs; production never exposes its runtime pooled
  `DATABASE_URL` to CI, only the direct URL for migrations.
