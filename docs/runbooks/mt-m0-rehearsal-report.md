### api-server test suite (full run, real DB, real Supabase auth)

Run: `CI=true REQUIRE_TEST_DATABASE=true TEST_DATABASE_URL=... DATABASE_URL=... SUPABASE_URL=... SUPABASE_SERVICE_ROLE_KEY=... pnpm --filter @workspace/api-server run test`

**Result: 136 tests, 96 pass, 30 fail, 10 cancelled** (96 + 30 + 10 = 136). The 10 cancelled are all `metrics.test.ts` subtests whose shared golden-fixture seed insert failed first (a bucket-(a) NOT NULL violation, below) — node:test cancels every sibling subtest once the parent seed it depends on throws, so these 10 are not a separate mystery, just downstream of the same root cause as the seed failure itself. This is the first time this milestone's changes have been exercised via a full, all-files-in-one-process run (every prior task's own verification ran only its own new/touched test file in isolation) — the failures below are genuine rehearsal findings, not something any single task's review could have caught.

Two distinct root causes, confirmed by comparison (running `inventory.test.ts` alone vs. as part of the full suite):

**(a) Already-known, already-documented fallout (no new information).** Tasks 4, 5, and 6's own reports flagged 13 pre-existing files that fail `pnpm --filter @workspace/api-server run typecheck` because their fixtures/handlers predate the new NOT NULL `facility_id`/`organization_id` columns (`alerts.ts`, `badTrays.ts`, `cycles.ts`, `facilityLogs.ts`, `growthProfiles.ts`, `sensors.ts`, `shipments.ts`, `tasks.ts`, `quickbooks.ts`, `overdue-scanner.ts`, and the `inventory.test.ts`/`shipments.test.ts`/`tasks.test.ts` test files' own `seed()` helpers). Running the full suite turns those same typecheck errors into real `23502 null value in column "facility_id"/"organization_id"` runtime failures at insert time — e.g. `tasks.test.ts`'s 5 status-filter tests, `inventory.test.ts`'s PATCH-concurrency tests (confirmed via isolated single-file run: same 8 failures reproduce with zero other files present). This is the same design tradeoff every prior task explicitly deferred to MT-M1 ("record, don't fix"), now visible at runtime instead of just typecheck.

**(b) New finding: cross-suite TRUNCATE CASCADE pollution — 6 files, not 3.** `run-tests.mjs` runs every `*.test.ts` file in one shared Node process, alphabetically sorted, against one shared database connection. A full audit of every `useDatabaseFixture([...])` call site found **six** files whose truncate list names `"facilities"`, `"organizations"`, and/or `"users"`: `facilities.test.ts` (`organizations, facilities, rooms, users`), `facility-readiness.test.ts` (`facility_readiness_events, facilities, organizations, users` — two describe blocks), `sensor-accounts.test.ts` (`sensor_accounts, organizations, users` — three describe blocks), `seedLots.test.ts` (`seed_lots, facilities, organizations`), `sensors-bulk.test.ts` (`sensors, channels, rooms, facilities, organizations`), and `wizard.test.ts` (`wizard_progress, users`). Before this milestone, `TRUNCATE ... CASCADE` on any of these had almost nothing to cascade into. Now that `facility_id` is a NOT NULL foreign key on 8 other tables (cycles, inventory_items, alerts, tasks, shipments, facility_logs, sensors, seed_lots) and `organization_id`/`user_id` fan out even further (`facilitiesTable.organizationId` itself FKs into `organizations`, and a dozen more tables FK into `users` — confirmed via `lib/db/src/schema/index.ts`), `TRUNCATE CASCADE` on any of `facilities`/`organizations`/`users` from any of these six files cascades transitively through Postgres's FK graph regardless of which table's name was actually passed, deleting rows other suites depend on — including the single seeded pilot-default facility (`id 1`) that `inventory.ts`'s and `seedLots.ts`'s own route handlers resolve via `SELECT id FROM facilities ORDER BY id LIMIT 1`. `facilities.test.ts` sorts alphabetically before `inventory.test.ts`, so by the time `inventory.test.ts`'s own tests run, the pilot-default facility row may already be gone — confirmed directly: `inventory.test.ts`'s "assigns a 4-char hex itemCode on create" test **passes** when run in isolation and **fails with a 500** when run as part of the full suite. This is a genuine new regression this milestone introduced into the test *infrastructure* (not production code — nothing in a real request path truncates `facilities` mid-flight), caught for the first time by this rehearsal because no earlier task ran the full cross-file suite together. `testDatabase.ts`'s own doc comment already states the intended contract ("reference data... facilities... can survive across suites") — these six files' truncate lists violate that contract themselves; they are the fix target, not the shared helper.

Root cause (a) was left deferred to MT-M1, consistent with every earlier task in this plan explicitly deferring cross-cutting fallout rather than expanding scope mid-task. Root cause (b) was fixed before merge (see below) — the final whole-branch reviewer judged it cheap, test-only, and a source of non-deterministic CI on `main` if left in place, unlike (a) which requires real session-based tenant resolution.

### Fix for (b), applied post-review

Removed `"facilities"`/`"organizations"`/`"users"` from the truncate lists in all 6 files. Each file's tests were read individually (not just the fixture line) to confirm no assertion relied on the shared tables being globally empty:

- `facilities.test.ts`, `sensor-accounts.test.ts`, `sensors-bulk.test.ts`, `wizard.test.ts`: every assertion was already scoped to an id/value returned from that test's own insert, or to `DEFAULT_TEST_USER.sub` (whose `organizationId` `seedTestUser`'s upsert resets on every call regardless of prior state) — dropping the shared-table truncation was a direct, no-behavior-change edit.
- `facility-readiness.test.ts`: same pattern; only `facility_readiness_events` needed truncating (each test creates its own fresh org+facility, and the "no facility yet" tests reset the test user's `organizationId` to null via `seedTestUser` explicitly).
- `seedLots.test.ts` needed a real design change, not just a line removal: its cross-facility-leak test relied on `TRUNCATE ... RESTART IDENTITY` to guarantee its own freshly-inserted "facility A" had the globally lowest id (since the lookup handler resolves the pilot-default facility via `ORDER BY id LIMIT 1`). Without truncation, some other suite's pilot-default facility could already have a lower id, silently invalidating the test's premise. Fixed by resolving "facility A" as *whichever facility currently has the lowest id* (the same query the route itself runs) instead of assuming a fresh insert wins the id race; "facility B" remains a fresh insert, guaranteed a higher serial id. This matches production reality (the pilot-default facility is whatever already exists) rather than fighting it.

Verified against the same disposable Supabase stack used for the rehearsal itself: typecheck shows the exact same 11-file baseline as before (no new errors from these 6 files); the full api-server suite improved from **96 pass / 30 fail / 10 cancelled** to **104 pass / 22 fail / 10 cancelled** — a diff of the failing-test-name lists before and after confirms 8 tests flipped from failing to passing (both `inventory.test.ts` itemCode tests, all 6 `sensor-accounts.test.ts` tests) and **zero new failures**. The remaining 22 failures + 10 cancelled are exactly root cause (a) (the already-documented 13-file list) — none of the 6 fixed files' own tests fail anymore, in isolation or in the full suite.

## Open items carried into MT-M1

1. **Task 4's 13-file typecheck/runtime fallout** (unchanged list: `alerts.ts`, `badTrays.ts`, `cycles.ts`, `facilityLogs.ts`, `growthProfiles.ts`, `sensors.ts`, `shipments.ts`, `tasks.ts`, `quickbooks.ts`, `overdue-scanner.ts`, `inventory.test.ts`, `shipments.test.ts`, `tasks.test.ts`) — these call sites need real facility/organization resolution (via `withTenantScope` once route handlers are rewired with real session context), not the pilot-default placeholder.
2. **Task 7's BYPASSRLS verification** — `scripts/ci/verify-db-role.mjs` was written but could not be run against a real staging/production connection in this session's environment (no live DB reachable outside the disposable rehearsal stack). This is a hard gate for MT-M1 (RLS cannot be trusted as an actual security control until this is verified against a non-BYPASSRLS role), not a blocker for MT-M0 itself since no route handler is wired to real tenant context yet. Still needs to be run once a real non-superuser Supabase role is provisioned per `docs/runbooks/tenancy-db-role.md`.
3. **`scripts/ci/check-tenant-scope.mjs` has a multi-line blind spot**, found during final whole-branch review: the guard only matches `db.select(...)...from(scopedTable)` on the *same line*, so it misses the standard multi-line Drizzle chain style — confirmed empirically that `seedLots.ts`'s own new lookup handler (multi-line, outside `withTenantScope`) slips through undetected and isn't in the baseline. Not a production-safety issue for MT-M0 (no handler is wired to real scope yet), but the check should be made multi-line-aware (or AST-based) before MT-M1 relies on it as a real gate, and the pilot-default accesses in `seedLots.ts`/`inventory.ts` should be added to the baseline so the ledger is accurate.
4. **Backfill migrations (0019, 0024) assume exactly one pre-existing facility/organization**, found during final whole-branch review: they assign every row to `(SELECT id FROM facilities/organizations ORDER BY id LIMIT 1)` unconditionally. Correct only because prod currently has exactly one pilot facility (documented in the migration headers) — migrations are not applied to prod in MT-M0, so this is an operational precondition to enforce (e.g. a `count(*) = 1` guard, or an explicit runbook check) before these migrations are ever run for real, not a code defect today.
5. **`organization_members`'s own RLS policy creates a chicken-and-egg for MT-M1**, found during final whole-branch review: the policy scopes on `app.org_id`, but resolving which org a user belongs to is precisely the query that must run *before* `app.org_id` is known. Under enforced RLS that lookup would return zero rows. MT-M1's session-resolution path will need a `BYPASSRLS`/`SECURITY DEFINER` route or a dedicated policy keyed on `user_id = auth.uid()` for this one lookup — captured here as a design constraint for whoever picks that up.
